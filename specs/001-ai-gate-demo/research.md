# Технические решения для AI Gate

Этот документ фиксирует решения для согласованной спецификации [`spec.md`](spec.md). Текущий этап заканчивается локальным запуском; публикация следует после проверки пользователем.

## Монорепозиторий и запуск TypeScript

- **Решение:** npm workspaces: `apps/web` для React + Vite + TypeScript, `apps/api` для Express 5 + TypeScript. Локальный API запускается на Node.js 24, который умеет выполнять поддерживаемый TypeScript без отдельного рантайм-транспилятора; переменные загружаются через `--env-file`.
- **Почему:** два процесса соответствуют двум слоям приложения, а один корневой `package-lock.json` и общие команды упрощают локальный запуск.
- **Альтернативы:** единый Next.js-проект уменьшил бы число процессов, но изменил бы согласованный React + Node/Express стек; `tsx` и `dotenv` добавили бы зависимости без потребности для выбранной локальной среды.
- **Проверка:** типы проверяются отдельно командой TypeScript, поскольку исполнение `.ts` в Node само по себе не является проверкой типов.

## Анонимная сессия

- **Решение:** сервер выдаёт случайный UUID в подписанной cookie `ai_gate_session` с `HttpOnly` и `SameSite=Lax`; `Secure` включается для HTTPS. `GET /api/session` возвращает UUID как метку для ключа `localStorage`. Право на серверную сессию подтверждает только подписанная cookie, а не значение из JSON.
- **Почему:** отдельная таблица сессий не нужна для записи пар запрос–ответ, а подпись позволяет отвергнуть подменённую cookie.
- **Альтернативы:** `express-session` потребовал бы дополнительного хранилища сессий; неподписанная cookie позволила бы клиенту назначать себе произвольный ID.
- **Граница:** при отсутствии или повреждении cookie сервер выдаёт новую сессию. История браузера читается только из ключа этой сессии.

## Потоковый ответ

- **Решение:** браузер отправляет `POST /api/chat` через `fetch`, API запрашивает `https://openrouter.ai/api/v1/chat/completions` с `stream: true`, разбирает SSE через `eventsource-parser` и посылает браузеру собственные события `delta`, `done`, `error`.
- **Почему:** `fetch` допускает тело POST и чтение потока; `EventSource` как клиентский API рассчитан на GET. Парсер обрабатывает границы сетевых чанков, которые не обязаны совпадать с границами SSE-событий.
- **Альтернативы:** WebSocket добавляет двусторонний протокол без нужды; ответ одним JSON нарушает требование стриминга.
- **Завершение:** сервер накапливает полный текст, вставляет одну запись в PostgreSQL и только после успешной вставки посылает `done`. При пустом/оборванном ответе или ошибке БД посылает `error`, не создавая успешную запись. Клиент сохраняет локальную историю только по `done`.

## Модель OpenRouter

- **Решение:** `OPENROUTER_MODEL` настраивается через серверное окружение, по умолчанию `openrouter/free`. API-ключ `OPENROUTER_API_KEY` остаётся только на сервере.
- **Почему:** [официальная страница Free Models Router](https://openrouter.ai/openrouter/free/apps) подтверждает ID `openrouter/free`, endpoint Chat Completions и `stream: true`. Конкретная бесплатная модель может меняться маршрутизатором; возможность задать другой ID делает локальную проверку устойчивее.
- **Альтернативы:** закрепить одну бесплатную модель означает зависеть от её текущей доступности; платную модель пользователь исключил из текущего объёма.
- **Ограничение:** доступность бесплатного маршрута и его лимиты зависят от OpenRouter и состояния ключа. Ошибки провайдера должны отображаться как ошибки, а не как выдуманный ответ.

## История на сервере и в браузере

- **Решение:** одна таблица `exchanges` содержит `id`, `session_id`, `prompt`, `answer`, `created_at`. Серверная история группируется по `session_id`. После `done` фронтенд добавляет полученную запись в `localStorage` под ключом `ai-gate:history:<sessionId>`.
- **Почему:** это буквальная минимальная реализация двух требуемых видов хранения. Разные cookie-сессии имеют разные ключи браузерной истории.
- **Альтернативы:** отдельная `sessions`-таблица полезна при сроке жизни и свойствах сессии; серверный `GET /api/history` позволил бы восстановить историю после очистки `localStorage`, но не заявлен в текущем этапе.
- **Ограничение:** очистка локального хранилища удаляет видимую историю браузера, хотя записи остаются в PostgreSQL. В этом этапе API не читает их обратно для интерфейса.

## Локальная инфраструктура и тестирование

- **Решение:** PostgreSQL запускается через Docker Compose с постоянным volume и SQL-инициализацией одной таблицы. Vitest проверяет поведение API и интерфейса; UI-тесты используют jsdom и React Testing Library. Проверки выполняются до реализации поведения по Red → Green → Refactor.
- **Почему:** БД можно запустить без ручной установки; тесты ловят ошибки границ ввода, сессий, разбора потока и сохранения истории.
- **Альтернативы:** внешняя управляемая БД пока добавила бы учётные данные и сетевую зависимость к локальной проверке; тесты только с моками не подтвердили бы схему PostgreSQL, поэтому нужен отдельный локальный сквозной прогон.
