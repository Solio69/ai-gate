# Implementation Plan: Минимальный AI Gate

**Branch**: `main` | **Date**: 2026-10-22 | **Spec**: [spec.md](spec.md)

**Input**: согласованная спецификация `specs/001-ai-gate-demo/spec.md`. Пользователь разрешил работу и коммиты непосредственно в `main`. Текущий результат — проверенный локальный запуск; публикация следует после проверки пользователем.

## Summary

Собрать минимальное приложение из React-интерфейса и Node/Express API. Посетитель получает подписанную анонимную cookie-сессию, отправляет запрос до 500 символов и видит потоковый ответ OpenRouter. После полного ответа API записывает пару в PostgreSQL под ID сессии и подтверждает завершение событием `done`; интерфейс сохраняет её в `localStorage` под ключом этой сессии. Регистрация, серверное чтение истории и публикация не входят в текущий этап.

## Technical Context

**Language/Version**: TypeScript для обоих приложений; Node.js 24 для локального API. Версии npm-пакетов фиксируются `package-lock.json` при реализации.

**Primary Dependencies**: npm workspaces; React, Vite; Express 5, `cookie-parser`, `pg`, `eventsource-parser`. `eventsource-parser` используется также браузерным приложением для ответа API. Для Node 24 не нужны `tsx` и `dotenv`: локальный запуск API использует выполнение `.ts` и `--env-file`.

**Storage**: PostgreSQL в Docker Compose (`exchanges`); браузерный `localStorage` с ключом по сессии. `.env` хранит только локальные секреты и игнорируется Git.

**Testing**: Vitest в обоих workspace; jsdom и React Testing Library для UI; локальная PostgreSQL для сквозной проверки.

**Target Platform**: локальный Windows-браузер с Node.js 24 и Docker Desktop. Vite proxy передаёт `/api` локальному Express, чтобы запросы и cookie шли через один origin.

**Project Type**: небольшое веб-приложение с отдельными frontend и API workspace.

**Performance Goals**: пользователь видит хотя бы первый фрагмент ответа до завершения генерации; числовая цель задержки в задании не установлена.

**Constraints**: 1–500 Unicode-символов после обрезки пробелов; одна бесплатная модель через настраиваемый `OPENROUTER_MODEL` с дефолтом `openrouter/free`; одна успешная запись на завершённый запрос; секреты только на сервере.

**Scale/Scope**: демонстрационный локальный сценарий для отдельных анонимных сессий. Нагрузочная цель, аккаунты и серверное восстановление истории не заявлены.

## Test-first and verification plan

### Подготовка инфраструктуры тестов

Сначала создать package scripts и установить зависимости. Запуск Vitest должен доходить до тестов; ошибки импорта, отсутствующего пакета или неработающего Docker **не считаются** фазой Red. Предусмотренные команды: `npm test -w apps/api`, `npm test -w apps/web`, затем `npm test --workspaces`.

### Red → Green → Refactor

1. **Сессия и валидация:** API-тесты проверяют выпуск cookie, повторное использование подписанной cookie, замену повреждённой cookie и границы 0/500/501 символов. UI-тесты проверяют форму и причину отказа. Настоящий Red — тест запускается и падает из-за отсутствующего поведения или неверного результата. Green — минимальный код сессии и формы. После упрощения rerun затронутых API/UI тестов.
2. **Стриминг:** тест API подменяет поток OpenRouter с разрезанными сетевыми чанками и требует последовательность `delta`, затем `done`; тест интерфейса требует видимый частичный текст до завершения. Ошибка upstream или обрыв должны приводить к ошибке без успешной записи. Green — минимальный SSE relay и чтение потока; затем rerun тестов контракта.
3. **История:** тест API требует ровно один INSERT полного ответа в `exchanges` под ID cookie и отсутствие INSERT при пустом/оборванном ответе или сбое БД. UI-тест проверяет запись только после `done`, восстановление после reload в той же сессии и отсутствие прежней истории при новом `sessionId`. Green — простой `pg` INSERT и работа с `localStorage`; после рефакторинга rerun обоих workspace.

### Уточнения интерфейса после локального тестирования

Сначала добавить поведенческие UI-тесты: Enter отправляет один запрос,
Shift+Enter сохраняет ввод новой строки, успешное завершение очищает только
исходный текст, а ошибка и новый ввод сохраняют поле. Длинные ответы истории
сокращаются после 180 Unicode-символов с многоточием; полный текст остаётся
в localStorage и раскрывается по кнопке. При обновлении состояние свёрнуто.
Изменения ограничены web workspace и документацией; API и схема БД не меняются.
Для ответа добавляется react-markdown без обработки сырого HTML: базовая разметка
показывается в текущем ответе и раскрытой истории. Сначала UI-тест на
форматирование и безопасное отображение, затем установка пакета и реализация.

просмотреть Markdown-разметку. Искусственный тест текста не нужен.

### Проверки без искусственных тестов

Для документации и конфигурации: `docker compose config`, `git diff --check`, сверка обязательных переменных `.env.example`, проверка `git check-ignore .env` и ручной просмотр соответствия `docs/` фактическому поведению. Не создавать тест, который лишь повторяет текст конфигурации.

### Итоговый прогон

Выполнить `npm test --workspaces`, `npm run typecheck --workspaces`, `npm run build --workspaces`; затем локально запустить PostgreSQL и приложение, отправить запрос с реальным ключом, наблюдать поток, обновить страницу, проверить новую сессию и строки БД. Конкретные команды, результаты и ограничения записать в `verification.md` как `Passed`, `Failed`, `Blocked` или `NotRun`. Перед коммитом сверить код с `spec.md`, просмотреть diff и отсутствие секретов. Коммит только согласованных путей в `main`, не затрагивая ранее staged изменения установки Spec Kit.
