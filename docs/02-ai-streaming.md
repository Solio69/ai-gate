# Фича 2. Потоковый ответ ИИ

**Состояние:** реализовано; браузерный сценарий с управляемым потоком прошёл. Реальный вызов OpenRouter с пользовательским ключом остаётся проверить вручную.

## Что видит пользователь

После отправки запроса текст появляется частями. Базовая Markdown-разметка ответа видна уже во время поступления текста. Успешно завершённый ответ остаётся целиком; при обрыве генерации или ошибке сохранения видна причина сбоя, а частичный текст не считается завершённой записью истории.

## Какие слои изменены

- **API:** сервер обращается к OpenRouter с ключом из окружения и моделью из `OPENROUTER_MODEL` (по умолчанию `openrouter/free`). Он разбирает поток провайдера и передаёт браузеру события `delta`, `done` и `error`. `done` отправляется только после успешной записи полной пары в PostgreSQL. Ожидание провайдера ограничено 120 секундами: сбой возвращает 502 до открытия потока или событие `UPSTREAM_ERROR` после него.
- **Интерфейс:** `fetch` читает SSE-ответ по мере поступления, дополняет показанный текст и различает завершение, ошибку и обрыв без `done`. Ответ форматируется библиотекой react-markdown без выполнения сырого HTML. Ключ OpenRouter не передаётся клиенту.

## Как проверено

Тесты API используют управляемый поток: проверяют разделённые сетевые фрагменты, порядок `delta` → `done`, ошибки провайдера, пустой ответ и сбой сохранения. Тесты интерфейса проверяют частичный текст до завершения и сообщения об ошибке. Общий прогон дал **24/24 теста API** и **23/23 тестов интерфейса**.

Дополнительно пройден локальный браузерный сценарий на собранном интерфейсе с настоящим API и PostgreSQL, но временным управляемым SSE upstream вместо OpenRouter. Первый фрагмент появился до `done`; после завершения был виден полный ответ, а после обновления страницы — локальная история. Временный сервер после проверки остановлен.

В прежнем локальном прогоне с пустым ключом API ожидаемо ответил 503. **Настоящая модель не проверена нами**; пользователь добавил ключ и может проверить её вручную по README.
