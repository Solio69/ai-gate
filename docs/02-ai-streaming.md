# Фича 2. Потоковый ответ ИИ

**Состояние:** реализовано; браузерный сценарий с управляемым потоком прошёл. Реальный вызов OpenRouter заблокирован отсутствующим ключом.

## Что видит пользователь

После отправки запроса текст появляется частями. Успешно завершённый ответ остаётся целиком; при обрыве генерации или ошибке сохранения видна причина сбоя, а частичный текст не считается завершённой записью истории.

## Какие слои изменены

- **API:** сервер обращается к OpenRouter с ключом из окружения и моделью из `OPENROUTER_MODEL` (по умолчанию `openrouter/free`). Он разбирает поток провайдера и передаёт браузеру события `delta`, `done` и `error`. `done` отправляется только после успешной записи полной пары в PostgreSQL. Ожидание провайдера ограничено 120 секундами: сбой возвращает 502 до открытия потока или событие `UPSTREAM_ERROR` после него.
- **Интерфейс:** `fetch` читает SSE-ответ по мере поступления, дополняет показанный текст и различает завершение, ошибку и обрыв без `done`. Ключ OpenRouter не передаётся клиенту.

## Как проверено

Тесты API используют управляемый поток: проверяют разделённые сетевые фрагменты, порядок `delta` → `done`, ошибки провайдера, пустой ответ и сбой сохранения. Тесты интерфейса проверяют частичный текст до завершения и сообщения об ошибке. Общий прогон дал **24/24 теста API** и **16/16 тестов интерфейса**.

Дополнительно пройден локальный браузерный сценарий на собранном интерфейсе с настоящим API и PostgreSQL, но временным управляемым SSE upstream вместо OpenRouter. Первый фрагмент появился до `done`; после завершения был виден полный ответ, а после обновления страницы — локальная история. Временный сервер после проверки остановлен.

При пустом `OPENROUTER_API_KEY` локальный API ожидаемо ответил 503. Поток с **настоящей моделью не проверен**: он заблокирован отсутствующим ключом и требует отдельного прогона после добавления ключа в игнорируемый `.env`.
