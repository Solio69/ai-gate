# Фича 3. История запросов и ответов

**Состояние:** реализовано; интеграционные тесты и локальный сквозной сценарий пройдены с управляемым upstream.

## Что видит пользователь

Завершённые пары запрос–ответ появляются в истории и восстанавливаются после обновления страницы в той же анонимной сессии. Новая сессия выбирает другой список. Ответ, завершившийся ошибкой, в историю успешных пар не попадает.

## Какие слои изменены

- **PostgreSQL:** таблица `exchanges` хранит ID пары, ID анонимной сессии, запрос, полный ответ и время записи. Индекс по `session_id`, `created_at` и `id` подготовлен для выборки записей одной сессии.
- **API:** после полного ответа провайдера сервер вставляет одну строку с ID из подписанной cookie и только затем отправляет событие `done`. При обрыве потока или ошибке БД успешное завершение не отправляется.
- **Браузер:** после `done` пара сохраняется в localStorage под ключом `ai-gate:history:<sessionId>`. Интерфейс читает этот список после обновления и игнорирует повреждённые локальные данные. Серверного маршрута чтения истории в текущем объёме нет.

## Как проверено

Три интеграционных теста с настоящей PostgreSQL проверили запись двух разных сессий, отсутствие частичной записи и ошибку записи в БД. Браузерные сценарии входят в **16/16 прошедших тестов интерфейса**. Контейнер БД запущен и проходит healthcheck на `127.0.0.1:5433`.

В локальном сквозном сценарии браузер сохранил завершённую пару в localStorage и восстановил её после обновления. Второй независимый cookie-клиент отправил запрос через тот же API; SQL показал **две строки с двумя разными `session_id`**. Для генерации использовался временный управляемый SSE upstream. После проверки обе строки удалены.

Повтор этого сценария с настоящими ответами OpenRouter **заблокирован отсутствующим ключом** в локальном `.env`.
